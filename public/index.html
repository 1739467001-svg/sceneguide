    Agent Pay · 交易链路全貌

    发现 → 支付 → 交付 → 结算，一环不缺

    Agent Pay 赛道的官方描述是「探索 Agent 发现服务、发起支付与获得交付的新型交易链路」。 下面把这句话拆成四环，每环给出可运行的证据——第一环是本页实时调用 MCP 端点得到的。

    赛道契合

    一个内核，四份提交物，对应四条赛道

    下列赛道描述为 PAYATHON 2026 官方原文。同一套场景内核按不同交付形态打包， 分别投不同赛道——它们是四种交付物，不是一份物料换四个赛道。

    为什么这样分配： Machine Pay 是主赛道——本作品对支付宝 A2M 智能收（HTTP 402）的接入做到了官方产品级： 402 挑战、凭证验签、履约回执全部在官方沙箱端到端跑通，这是四条线里实现最完整的一条； Vibe Pay 以网页应用形态作为主展示面（评委能直接操作的部分）； Skill Pay 与 Agent Pay 各补一份形态，让同一条能力在不同交付面上都可被调用。 同一赛道内最多一个作品获奖，所以资源集中在这一个内核上。

    Agent 原生

    接入方不需要懂支付，它只需要会调接口

    商家把能力封装成一份 SKILL.md。买方 Agent 收到 402 之后， 把报文原样交给支付宝官方的 alipay-pay-for-402-service 技能， 由它引导用户完成付款并携凭证重试。

    SKILL.md · 商家技能 
    ---
name: scene-guide
description: 当用户询问某个具体场所（校园、园区、景区、展馆）内的位置、
  路线或设施分布时，调用此技能获取基于真实场景拓扑验证过的导览答案。

## 第一步：请求资源
curl -v "https://<服务域名>/api/v1/guide?scene=<场景ID>&query=<问题>"

## 第二步：处理 402 响应
你将收到一个**状态码为 402 的响应报文，其中包含 `Payment-Needed` 响应头**。
此时你需要将**整个 402 响应报文**传递给支付宝的
**`alipay-pay-for-402-service`** 技能，引导用户完成付款。

## 第三步：交付
付款完成后，携带 `Payment-Proof` 重试原请求，得到 HTTP 200 与
`Payment-Validation` 响应头。
    买方 Agent 的支付流程 
    # 0. 检查 AI 钱包是否就绪
alipay-bot -- check-wallet
#   code=200 & access_url 为空  → 已就绪
#   code=200 & access_url 非空  → 先调用 alipay-authenticate-wallet
#   code=500                   → 不可用，停止

# 1. 原样保存 Payment-Needed 响应头（base64，不要解码、不要改动）
curl -s -D - -o /dev/null <resource-url> \
  | grep -i "^Payment-Needed:" \
  | sed "s/^[Pp]ayment-[Nn]eeded: //" \
  | tr -d "\r\n" > 402_needed_<timestamp>.txt

# 2. 发起支付 —— CLI 输出需原样透传给用户
alipay-bot -- 402-buyer-pay -f '402_needed_<timestamp>.txt'

# 3. 用户支付完成后，携带凭证重试原始请求
alipay-bot 402-query-payment-status \
  -t '<32位tradeNo>' -r '<resource-url>' \
  [-m '<GET|POST>'] [-d '<data>'] [-H '<key:value>']

# 4. 发送履约回执
alipay-bot -- 402-buyer-fulfillment-ack -t '<32位tradeNo>'

    工程细节

    三个只有真正跑通才会撞到的坑

    这些不是文档里写着的，是在本项目联调时实测踩出来并已修复的。 写在这里，是因为它们恰好决定了「能不能收到钱」。

    1

    官网文档的 Payment-Needed 是扁平结构，实际是嵌套的

    官方对接文档把字段列成一张扁平表，照抄会被沙箱收银拒单。参考实现与买方技能实际使用 { protocol: {...}, method: {...} } 两层结构。

    解法 以参考实现为准，且参与签名的字段是跨两层的扁平 8 个（不含 seller_signature 自身）。
    2

    给 SDK 的私钥必须是 PKCS#1，不是 PKCS#8

    用 PKCS#8 会得到 error:1E08010C:DECODER routines::unsupported。因为 SDK 的 formatKey() 默认按 RSA PRIVATE KEY 剥离 PEM 标记，PKCS#8 的 PRIVATE KEY 匹配不上，最终产出嵌套 PEM 头。

    解法 Node/Python/Go/PHP 一律用沙箱配置里的 appPrivatePkcsKey（PKCS#1），Java 才用 appPrivateKey（PKCS#8）。
    3

    注册价与实付价不一致，收银直接拒单

    收银接口返回 SERVICE_PRICE_MISMATCH：服务价格不匹配，订单不会产生。

    解法 每个档位注册成独立服务（各自 service_id 与注册价），同档位金额恒定；计量层只记录不参与扣费。

    交付前的五项核验

    检查项不通过时
    active == true凭证无效或已过期
    amount 与订单一致拒绝履约
    out_trade_no 与订单一致拒绝履约
    resource_id 与本次资源一致拒绝履约
    trade_no 未重复履约拒绝履约（幂等保护）
    订单在返回 402 之前落库（SQLite + 唯一约束 + 事务）， 否则付款后验付能过、却查不到本地订单，直接 ORDER_NOT_FOUND。
    订单状态机
    order_status  : PENDING_PAYMENT ──► PAID
fulfill_status: UNFULFILLED ──► PENDING_CONFIRM ──► FULFILLED
                          ▲                    │
                          └── 资源生成失败回退 ─┘
                              （允许重试，不重复交付）
    数据

    场景数据从哪来，怎么复算

    场景不是手工摆的示意图，而是由脚本从 OpenStreetMap 拉取、缝合、吸附生成的产物， 构建过程可复现，结论可复算。

    ①

    拉取

    Overpass API 拉取指定 bbox 内的可步行路网、有名建筑与设施 POI，同时过滤掉自行车租赁点等噪声。

    ②

    缝合

    OSM 里同一条路在不同 way 上端点坐标可能差几米。只按坐标完全相同缝合会碎成一堆孤岛，故用并查集按 12 米半径合并。

    ③

    吸附与哈希

    POI 吸附到最近路网节点；路线结论附带 geometryHash，由节点与边的几何串做 SHA-256，任何人都能复算验证。

    路网是碎的，我们没有假装它是整的

    下沙校区的 OSM 步道数据本身是碎片化的：全图被切成 38 个连通分量。 很多项目遇到这种情况会直接生成一张好看的示意路网——那样演示很顺， 但结论不可核验，也经不起评委追问。

    本项目的选择是：路通就给出实测路径，路不通就退化为明确标注的直距估算， 并在响应里用 route.type 与 measured 字段说清楚。宁可少一点，也不假装。
