    与支付宝官方接口的对齐

    本作品只使用官方 AI 付（按量付费 / A2M）要求的接口，不自造协议、不绕过收银台。 下表逐条列出调用的官方接口、它解决的问题与本系统的实测状态。

    官方接口 / 协议元素解决什么本系统状态
    alipay.aipay.agent.payment.precreate
    按量付费预下单    		 向支付宝创建预下单，取得 amt_pre_pay_id 已实现（src/a2m/client.js）·生产环境输出 amtPaymentLink 头
    沙箱不调用（沙箱只有固定 mock 服务），生产开关见 config/production.json
    Payment-Needed 响应头
    商家本地构造 + RSA2 签名    		 把「买什么、多少钱、给谁」以可验签的形式交给买方 已实现 · 官方沙箱端到端跑通
    嵌套结构 + 扁平签名子集，官方文档未写明，见技术规格 §0.5
    alipay.aipay.agent.payment.verify 校验买方的支付凭证与交易归属 已实现 · 在此之上做五项业务核验（active / amount / out_trade_no / resource_id / trade_no 防重）
    alipay.aipay.agent.fulfillment.confirm 履约回执：告诉支付宝「资源已交付」 已实现 · 状态机 UNFULFILLED → PENDING_CONFIRM → FULFILLED
    Payment-Validation 响应头 把可归属的交付凭证回传给买方 已实现 · 附证据哈希，可复算
    沙箱收银（alipay-bot / 官方买方技能） 买家侧完成付款的官方路径 已打通 · 站内「走一遍真实沙箱支付」走的就是它
    硬性约束：付费资源 URL 必须 HTTPS 官方买方 CLI 对资源地址的前置校验 已满足：全站 HTTPS（含裸 IP 的 Let's Encrypt 短期证书方案， 12 小时自动续期）——地址若是 http://，官方工具下单会直接失败
    为什么接口数只有这些：按量付费官方只要求实现 3 个接口（402 / 验付 / 履约确认）， 而网站支付与 APP 支付要 6 个（下单 / 查询 / 退款 / 退款查询 / 关闭 / 异步通知）。 这也是本项目选择按量付费赛道的工程理由之一。

    官方支付能力的两族，以及我们为什么这么分工

    支付宝开放平台当前公开的支付类 MCP 能力分两族。本作品不是只用其中一族， 而是按「谁来付、谁来感知」做了分工：

    官方能力族官方工具 / 接口谁在付在本作品中的角色
    AI收
    HTTP 402 · 按量付费    		 Payment-Needed / Payment-Proof /
    payment.verify / fulfillment.confirm /
    payment.precreate    		 买家的 Agent 代用户付款 主链路：Agent 原生的「发现→支付→交付」，本作品按此实现并被官方买方脚本判定通过
    支付 MCP Server
    网页 / 手机支付    		 create-web-page-alipay-payment /
    create-mobile-alipay-payment /
    query-alipay-payment /
    refund-alipay-payment /query-alipay-refund    		 人自己扫码或登录付款 互补路径：人付款时由官方能力发起与查询；本服务提供 AP_NOTIFY_URL 异步通知端点接收结果（官方要求「支付结果以异步通知或查询接口为准」）， 并已实现防篡改与幂等
    分工的理由：402 协议解决的是「Agent 买 API」——买方是程序，凭证随请求回传， 天然可靠；而「人买内容」没有 Payment-Proof 回传路径， 必须靠官方的异步通知或查询接口才知道钱到账了。两条路各用其长， 而不是自己造一套支付。
    官方条款对照（据开放平台《AI收 · 接入准备 / 产品介绍》）：
    准入支持企业账号、个人账号、个体工商户——本作品以个人账号主体接入
    费率单笔 1.0%；个人开发者 2026.4.15–12.31 零费率（本站「个人开发者费率 0%」即源于此）
    结算默认实时到账商家签约账号的支付宝余额；新签约未满 90 日或连续交易未满 30 日的次日结算，当日资金见「对账中心 › 不可用余额」
    退款默认交易后 12 个月内可原路退款，退款时服务费一并退回；本站沙箱环境退款接口不可用，故实现为「权益即时回收 + 工单留痕 + 订单标注」，生产环境按官方退款能力执行
    买方前提用户在支付宝 App 开通 AI 钱包并开启支付功能，智能体方能代其完成付款
    调试环境官方说明「AI收 产品暂不支持沙箱调试」——本作品使用的是支付宝官方 Skill 提供的匿名沙箱（api_mock_service_id + 官方沙箱收银），正式环境需注册真实 service_id 后切生产
    最硬的一项证据：被支付宝官方买方脚本买通过。
    上面这些接口不是我们自己说好使就算数——我们用支付宝官方写的买方脚本 local_402_sandbox_pay.py（官方 Skill 内置）去买本服务： 它自己发起请求、拿到 402 账单、走官方沙箱收银付款、携 Payment-Proof 重试， 然后由官方脚本自己校验交付证据。
    官方脚本的结论原文：「AI 按量付费沙箱服务端联调通过」。
    你自己也能验（只需要装有支付宝官方买方 CLI alipay-bot， 不需要我们仓库里的任何东西）——直接让它来买本服务：

    交易链路全貌 · 四环可查

    发现 → 支付 → 交付 → 结算，一环不缺

    按量付费（Machine Pay）的买方天然就是 Agent——所以官方对「Agent 发现服务、 发起支付、获得交付」这条新型交易链路的描述，正是本作品逐环跑通的那条链路。 下面把它拆成四环，每环给出可运行的证据——第一环是本页实时调用 MCP 端点得到的， 最后一环是支付宝官方口径与本服务提供的回调通道。

    赛道契合

    一个内核，主投 Machine Pay

    下列赛道描述为 PAYATHON 2026 官方原文。本作品的唯一投递赛道是 Machine Pay： 它对支付宝 A2M 智能收（HTTP 402）的接入做到了官方产品级——402 挑战、凭证验签、 五项核验、幂等履约与履约回执全部在官方沙箱端到端跑通，是这四条线里实现最完整的一条。

    为什么聚焦一条赛道： 官方规则明确「同一作品不得跨赛道重复投稿」，且「同一赛道内最多一个作品获奖」。 本作品的核心是同一套能力（402 按量付费 + 真实地理拓扑 + 可核验交付）， 拆成四份投递既是重复投稿，也会在四个赛道里同时损失评委注意力。 所以资源全部压在 Machine Pay 的实现深度上——把这一个赛道做到可被独立复核， 比在四条赛道上各交一份浅的更划算。

    Agent 原生

    接入方不需要懂支付，它只需要会调接口

    商家把能力封装成一份 SKILL.md。买方 Agent 收到 402 之后， 把报文原样交给支付宝官方的 alipay-pay-for-402-service 技能， 由它引导用户完成付款并携凭证重试。

    SKILL.md · 商家技能 
    ---
name: scene-guide
description: 当用户询问某个具体场所（校园、园区、景区、展馆）内的位置、
  路线或设施分布时，调用此技能获取基于真实场景拓扑验证过的导览答案。
---

## 第一步：请求资源
curl -v "https://<服务域名>/api/v1/guide?scene=<场景ID>&query=<问题>"

## 第二步：处理 402 响应
你将收到一个状态码为 402 的响应报文，其中包含 Payment-Needed 响应头。
此时你需要将整个 402 响应报文传递给支付宝的
alipay-pay-for-402-service 技能，引导用户完成付款。

## 第三步：交付
付款完成后，携带 `Payment-Proof` 重试原请求，得到 HTTP 200 与
`Payment-Validation` 响应头。
    买方 Agent 的支付流程 
    # 0. 检查 AI 钱包是否就绪
alipay-bot -- check-wallet
#   code=200 & access_url 为空  → 已就绪
#   code=200 & access_url 非空  → 先调用 alipay-authenticate-wallet
#   code=500                   → 不可用，停止

# 1. 原样保存 Payment-Needed 响应头（base64，不要解码、不要改动）
curl -s -D - -o /dev/null <resource-url> \
  | grep -i "^Payment-Needed:" \
  | sed "s/^[Pp]ayment-[Nn]eeded: //" \
  | tr -d "\r\n" > 402_needed_<timestamp>.txt

# 2. 发起支付 —— CLI 输出需原样透传给用户
alipay-bot -- 402-buyer-pay -f '402_needed_<timestamp>.txt'

# 3. 用户支付完成后，携带凭证重试原始请求
alipay-bot 402-query-payment-status \
  -t '<32位tradeNo>' -r '<resource-url>' \
  [-m '<GET|POST>'] [-d '<data>'] [-H '<key:value>']

# 4. 发送履约回执
alipay-bot -- 402-buyer-fulfillment-ack -t '<32位tradeNo>'

    幂等交付

    资源只生成一次。履约回执失败时状态停在 PENDING_CONFIRM，允许同一笔凭证重试，不会重复交付、也不会重复消耗算力。

    工程细节

    三个只有真正跑通才会撞到的坑

    这些不是文档里写着的，是在本项目联调时实测踩出来并已修复的。 写在这里，是因为它们恰好决定了「能不能收到钱」。

    1

    官网文档的 Payment-Needed 是扁平结构，实际是嵌套的

    官方对接文档把字段列成一张扁平表，照抄会被沙箱收银拒单。参考实现与买方技能实际使用 { protocol: {...}, method: {...} } 两层结构。

    解法 以参考实现为准，且参与签名的字段是跨两层的扁平 8 个（不含 seller_signature 自身）。
    2

    给 SDK 的私钥必须是 PKCS#1，不是 PKCS#8

    用 PKCS#8 会得到 error:1E08010C:DECODER routines::unsupported。因为 SDK 的 formatKey() 默认按 RSA PRIVATE KEY 剥离 PEM 标记，PKCS#8 的 PRIVATE KEY 匹配不上，最终产出嵌套 PEM 头。

    解法 Node/Python/Go/PHP 一律用沙箱配置里的 appPrivatePkcsKey（PKCS#1），Java 才用 appPrivateKey（PKCS#8）。
    3

    注册价与实付价不一致，收银直接拒单

    收银接口返回 SERVICE_PRICE_MISMATCH：服务价格不匹配，订单不会产生。

    解法 每个档位注册成独立服务（各自 service_id 与注册价），同档位金额恒定；计量层只记录不参与扣费。

    交付前的五项核验

    检查项不通过时
    active == true凭证无效或已过期
    amount 与订单一致拒绝履约
    out_trade_no 与订单一致拒绝履约
    resource_id 与本次资源一致拒绝履约
    trade_no 未重复履约拒绝履约（幂等保护）
    订单在返回 402 之前落库（SQLite + 唯一约束 + 事务）， 否则付款后验付能过、却查不到本地订单，直接 ORDER_NOT_FOUND。
    订单状态机
    order_status  : PENDING_PAYMENT ──► PAID
fulfill_status: UNFULFILLED ──► PENDING_CONFIRM ──► FULFILLED
                          ▲                    │
                          └── 资源生成失败回退 ─┘
                              （允许重试，不重复交付）
    数据

    场景数据从哪来，怎么复算

    场景不是手工摆的示意图，而是由脚本从 OpenStreetMap 拉取、缝合、吸附生成的产物， 构建过程可复现，结论可复算。

    ①

    拉取

    Overpass API 拉取指定 bbox 内的可步行路网、有名建筑与设施 POI，同时过滤掉自行车租赁点等噪声。

    ②

    缝合

    OSM 里同一条路在不同 way 上端点坐标可能差几米。只按坐标完全相同缝合会碎成一堆孤岛，故用并查集按 12 米半径合并。

    ③

    吸附与哈希

    POI 吸附到最近路网节点；路线结论附带 geometryHash，由节点与边的几何串做 SHA-256，任何人都能复算验证。

    路网是碎的，我们没有假装它是整的

    下沙校区的 OSM 步道数据本身是碎片化的：全图被切成 38 个连通分量。 很多项目遇到这种情况会直接生成一张好看的示意路网——那样演示很顺， 但结论不可核验，也经不起评委追问。

    本项目的选择是：路通就给出实测路径，路不通就退化为明确标注的直距估算， 并在响应里用 route.type 与 measured 字段说清楚。宁可少一点，也不假装。
