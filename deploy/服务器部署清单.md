## 🔴 2026-11-22 部署事故复盘：四个坑与最终修复（先读这节）

> 本次把 11-20 的新版代码真正部署上线，连续踩了四个坑。前三个互相叠加，
> 造成「deploy.sh 每次都报成功、线上却一直停在 11-06 旧版」的假象。

| # | 坑 | 现象 | 修复 |
|---|---|---|---|
| ① | **deploy.sh「假部署」**：只上传代码 + `compose restart`，代码在镜像里 | restart 不换镜像，新代码从未生效 | 已改为 `up -d`（2026-11-21） |
| ② | **compose 的 `./app:/app` 挂载遮蔽**：容器读宿主 `app/` 目录，而 deploy.sh 把代码解压到 `APP_DIR/` 根 | 解压的新代码永远进不了容器视线（线上停 11-06 的真正根因） | deploy.sh 改为解压进 `${APP_DIR}/app/`（compose 挂载的正是它） |
| ③ | **compose 的 image 行是裸 node:22 基镜像**：本地构建上传的 `sceneguide:1.0` 全程被无视；且启动时现场 `npm ci`（内存雷区） | 预构建镜像白做；服务器 OOM 风险 | 见下「最终架构」——保留 node:22 + 运行时 npm ci（历史稳定栈） |
| ④ | **better-sqlite3 v13.0.3 linux-x64 预编译产物有 bug**：文件型 DB（WAL）一打开就 SIGSEGV（exit 139），`:memory:` 正常；npmmirror 与 GitHub 官方 prebuilt **都坏** | 本机 QEMU 构建与服务器本地构建的 node:20 镜像全部崩溃循环；同字节二进制在全新容器却通过（复现条件未分离，记录在案） | **升级 better-sqlite3 13.2.0**（上游 13.1.1 修复）；并回退到 node:22 + 运行时 npm ci 栈 |
| ⑤ | **单文件 scp 发布造成版本错配**：`scp src/routes/guide.js` 只更新一个文件，服务器 `app/` 里其它文件仍是旧版 → `repository.js` 缺 `computeQuestScore` 导出 → ESM 加载失败 → 容器崩溃循环 → 全站 502 | 2026-11-23 实测踩到（本地 76/76 全绿，线上却 502） | **禁止单文件 scp 发布，一律走 `deploy.sh` 全量发布**（tar 整个代码包 → 解压覆盖 `app/` → `compose up -d --force-recreate`） |

**最终架构（2026-11-22 生效，aliyun 生产现况）**：

```
deploy.sh: tar 代码包 → scp → 解压进 /srv/apps/sceneguide/app/
           → cp app/data/scenes/*.json → /srv/apps/sceneguide/scenes/
           → docker compose up -d --force-recreate
compose:   node:22-bookworm 基镜像 + 启动时 npm ci（deps 卷缓存）
           ./app:/app（代码 + 沙箱密钥权威副本） · ./data:/app/data（DB） · ./scenes:/app/scenes:ro
回滚:      docker-compose.yml.bak-sg60-20261122 是事故前备份；app/ 旧代码被 tar 直接覆盖（接受，git 是权威）
```

**验证基线（2026-11-22 14:55）**：healthz ok（sandbox 双库 ok）；公网 `/account.html` `/api/v1/me` `/introduction.html` `/api/v1/growth` 全 200（此前 404）；`/api/v1/guide` 402；全量回归 **75/76**。
唯一失败项 = `verify-render.mjs`（第 20 项）：**本机 Clash 对直连 IP 121.43.80.231 的干扰**——无头 Chrome 打开该 IP 直接 chrome-error（同环境 curl 全通、能开百度；内置浏览器完整渲染 `scene3d:true`）。**非作品问题**；跑渲染验收前请关系统代理/VPN 或为该 IP 配直连规则。

**遗留待查**：node:20 镜像里 better-sqlite3 文件 DB 段错误的确切触发条件（同字节二进制、同基镜像、全新容器通过；镜像容器必崩——X1 已证明与 bs3 文件无关，Y5 env -i 干净环境仍崩）。已用「回退稳定栈」绕过，不影响业务。

## 【已废弃 · 保留记录】推荐路径：60.205.204.162 + 独立端口 3100

> 该机 2026-11 中旬已不可达（SSH 22 banner 超时，实例死亡）。本节原文保留，
> 仅作为「当初为什么这么设计」的记录；若 sg60 恢复，本节仍可按原样执行。

### 1. 阿里云控制台放行端口（你来，约 2 分钟）

ECS 控制台 → 实例 `60.205.204.162` → 安全组 → 配置规则 → **入方向添加**：

| 协议 | 端口 | 授权对象 | 描述 |
|---|---|---|---|
| TCP | 3100 | 0.0.0.0/0 | sceneguide-demo |

同时检查 **22 端口**是否对本机 IP 放行——被拦了就顺手加一条（授权对象填你的出口 IP 更安全）。

### 2. 服务器侧初始化（一次性，SSH 进去后）

```bash
# Node ≥ 20（Ubuntu/Debian）
curl -fsSL https://deb.nodesource.com/setup_20.x | bash - && apt-get install -y nodejs
# 或 CentOS/Alibaba Cloud Linux: curl -fsSL https://rpm.nodesource.com/setup_20.x | bash -

useradd -m -s /bin/bash sguser || true
mkdir -p /opt/sceneguide && chown sguser /opt/sceneguide
# 现网走 Docker Compose，不装裸机 systemd 单元（那是已退役路径，配置在 deploy/retired/）
```

### 3. 发布（每次更新后）

```bash
SERVER=root@60.205.204.162 bash deploy/deploy.sh
# deploy.sh 支持参数：
#   PORT=3100            远端服务端口（默认 3000）
#   HEALTH_PATH=/healthz 健康检查路径
```

### 4. 沙箱密钥（让线上先跑通演示）

```bash
scp scene-guide/.alipay-sandbox.json root@60.205.204.162:/opt/sceneguide/scene-guide/
ssh root@60.205.204.162 \
  "chown sguser /opt/sceneguide/scene-guide/.alipay-sandbox.json && chmod 600 $_"
```

### 5. 验证（本机直接打外网地址）

```bash
curl -i "http://60.205.204.162:3100/api/v1/guide?scene=zjgsu-xiasha&query=test"
#   期望：HTTP 402 + Payment-Needed 头
BASE_URL=http://60.205.204.162:3100 bash scripts/verify.sh
#   期望：39 项全绿
```

### 6. 提交 service_id 注册

用 **`提交材料/服务注册信息包.md`** 逐字段提交，
可访问地址填 `http://60.205.204.162:3100/api/v1/guide`。

### 7. 域名备案通过后（升级）

1. `sudo bash deploy/https/enable-https.sh <你的域名>` —— 自动装 certbot、签证书、
   装独立 server 块（80 跳 HTTPS + 443 反代 `/sceneguide/`），`nginx -t` 不过自动回滚
2. `config/production.json` 写入生产密钥 + 真实 service_id → 启用 `ALIPAY_ENV=production` → 重启
3. `BASE_URL=https://<域名>/sceneguide bash scripts/verify.sh`（88 项）
4. 更新 service 注册信息里的地址为域名版；页面对外链接统一换新域名
5. HTTPS 生效后 Service Worker / PWA「一键安装」自动恢复（安全上下文）

## 【已发生】备选路径成了现实：aliyun（121.43.80.231）
